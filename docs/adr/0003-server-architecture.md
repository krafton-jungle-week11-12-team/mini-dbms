# ADR 0003. 서버 구조와 스레드 풀

2026-11-16

## 후보

**엔진과 서버 연결**
- A. 한 프로세스 안에서 함수 호출 (`engine.execute(sql)`)
- B. 엔진을 별도 서버로 띄우고 네트워크로 호출

**스레드 풀**
- (1) `ThreadingHTTPServer`
- (2) `ThreadPoolExecutor`에 요청 넘기기
- (3) 직접 만든 풀 (`queue.Queue` + 워커 N개)

**락**
- 전역 락 하나
- 테이블별 락
- 테이블별 읽기/쓰기 락

## 비교

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| A. 함수 호출 | 단순하고, CLI와 서버가 같은 엔진을 그대로 써요 | 엔진만 따로 늘리기 어려워요 |
| B. 별도 서버 | 엔진과 서버를 따로 늘릴 수 있어요 | 프로토콜이 하나 더 생기고, 이번 과제에서는 얻는 게 적어요 |
| (1) `ThreadingHTTPServer` | 코드가 가장 짧아요 | 요청마다 스레드를 새로 만들어서 스레드 풀이 아니에요 |
| (2) `ThreadPoolExecutor` | 표준 풀이라 안정적이에요 | 큐 크기를 정하기 어렵고 내부가 가려져 있어요 |
| (3) 직접 만든 풀 | `Queue(maxsize=N)`로 큐 크기를 정하고, 요청 할당 과정을 코드로 보여줘요 | 30~40줄을 직접 짜야 해요 |
| 전역 락 | 가장 쉬워요 | 모든 요청이 한 줄로 처리돼요 |
| 테이블별 락 | 쉽고, 다른 테이블끼리는 동시에 처리해요 | 같은 테이블의 SELECT끼리도 기다려요 |
| 테이블별 읽기/쓰기 락 | SELECT끼리 동시에 처리해요 | 표준 라이브러리에 없어서 직접 만들어야 해요 |

## 결정

- 서버와 엔진은 한 프로세스에서 `engine.execute(sql)` 함수로 연결해요.
- 서버는 `http.server.HTTPServer`를 상속해 요청을 `queue.Queue(maxsize=N)`에 넣고, 시작할 때 만든 워커 N개가 꺼내 처리해요. 엔드포인트는 `POST /query` 하나예요.
- 락은 테이블별 락으로 시작하고, 시간이 남으면 테이블별 읽기/쓰기 락으로 바꿔요.
- 워커 수와 큐가 가득 찼을 때의 처리(대기 또는 거절)는 Phase 3 설계에서 정해요.

## 결정 이유

- lms가 "Phase 1+2를 내부 엔진으로 그대로 활용"을 요구해서, 엔진을 함수로 부르는 구조가 가장 잘 맞아요.
- lms가 스레드 풀을 요구해서 요청마다 스레드를 만드는 `ThreadingHTTPServer`는 맞지 않아요. 직접 만든 풀은 큐가 가득 찼을 때의 처리까지 설명할 수 있어요.
- 마감이 가까워서 락은 쉬운 것부터 시작해요. INSERT의 id 발급, CSV 덧붙이기, B+ 트리 삽입을 같은 락 안에 묶으면 id 중복과 행 섞임을 막을 수 있어요.
