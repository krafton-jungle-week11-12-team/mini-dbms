# Phase 4 테스트 케이스

이 문서를 읽으면 Phase 4 스레드 풀이 요청을 큐에 넣고, 가득 차면 거절하고, 예외와 timeout 뒤에도 계속 동작하는지, 테이블 락이 동시 요청에서 데이터를 지키는지 어떻게 테스트하는지 알 수 있어요.
기대 결과는 [Phase 4 설계](../design/phase4.md)와 [Phase 4 요구사항](../requirements/phase4.md)을 따라요.

## 작성 방식

- 스레드 테스트(`T-TP`)는 임시 폴더(`tmp_path`)를 데이터 폴더로 서버를 띄우고 실제 HTTP 요청을 보내요. 워커와 큐가 가득 찬 상황은 `QueryServer(workers=1, queue_size=...)`처럼 작게 줘서 만들어요.
- "바디를 보내지 않는 연결"은 소켓으로 `POST /query` 헤더와 `Content-Length: 10`만 보내고 바디는 보내지 않은 연결이에요. 워커가 바디를 기다리느라 붙잡혀 있게 만들 때 써요.
- 워커가 연결을 가져갔는지는 메인 스레드가 받은 연결 수와 `server.jobs.qsize()`를 같이 보고 확인해요. `qsize() == 0`만으로는 워커가 가져간 건지, 메인 스레드가 아직 받지 않은 건지 구분할 수 없어서, `process_request`를 감싸 받은 연결 수를 세요. 앞 연결이 워커에 잡히기 전에 다음 연결을 보내면 순서가 매번 달라질 수 있어요.
- 동시성 테스트(`T-LK`)는 락이 없으면 실패해야 의미가 있어요. 경합이 드물게 일어나는 곳은 `sleep`을 끼워 넣거나 요청 수를 늘려서 끼어들 틈을 일부러 만들어요.
- `T-LK-03` ~ `T-LK-05`는 HTTP를 거치지 않고 `Executor`를 직접 호출해요. 빠르고, 결과가 매번 같게 나와요.
- ID는 요구사항 ID에 맞춰 스레드는 `T-TP-01`, 동시성은 `T-LK-01`부터 붙여요.
- 스키마는 `users(id INT, name TEXT, age INT)`이고, id는 실행기가 부여해요.
- 상태는 `미실행`, `통과`, `실패` 중 하나예요.

| T-TP-01 | 스레드 | 메인 스레드는 작업을 큐에 넣는다 | `QueryServer(workers=1, queue_size=4)` 실행. 바디를 보내지 않는 연결 A로 워커 1개를 붙잡아 둠(받은 연결 1개, `qsize() == 0` 확인) | 정상 SELECT 요청 B, C를 보냄 | B, C의 응답이 오기 전에 `server.jobs.qsize() == 2`. A를 닫으면 B, C 모두 200 | 미실행 | `TP-02` |
| T-TP-02 | 스레드 | 놀고 있는 워커가 없으면 요청이 작업 큐에서 기다린다 | `workers=1, queue_size=4`. 바디를 보내지 않는 연결 A로 워커를 붙잡아 둠(받은 연결 1개, `qsize() == 0` 확인) | 요청 B를 보내고 0.5초 기다린 뒤 A를 닫음 | A를 닫기 전까지 B는 응답을 받지 못함. A를 닫은 뒤 B는 200 | 미실행 | `TP-05`. 워커 수가 0인 경우가 아니라 모든 워커가 처리 중인 경우예요. `workers=0`은 설계에서 `ValueError`로 막아요 |
| T-TP-03 | 스레드 | 작업 큐가 가득 찼다면 503을 응답한다 | `workers=1, queue_size=1`. 바디를 보내지 않는 연결 A로 워커를 붙잡고(받은 연결 1개, `qsize() == 0` 확인), 연결 B로 큐 한 칸을 채움(받은 연결 2개, `qsize() == 1` 확인) | 정상 SELECT 요청 C를 보냄 | C는 1초 안에 503, `ok: false`, `error.code: "SERVICE_UNAVAILABLE"`, `Retry-After: 1` 헤더. A, B를 닫고 큐가 빈 뒤(`qsize() == 0`) 보낸 요청은 200 | 미실행 | `TP-03`. A, B를 닫은 바로 뒤에는 워커가 아직 B를 꺼내지 않아 큐가 가득 차 있을 수 있어서, 큐가 빌 때까지 기다린 뒤 보내요 |
| T-TP-04 | 스레드 | 요청 처리 중 예외가 나도 워커가 스레드 풀로 돌아간다 | `workers=1`. `QueryHandler._execute`가 `RuntimeError`를 던지도록 교체 | 요청 하나를 보낸 뒤 교체를 되돌리고 SELECT를 보냄 | 첫 요청은 응답 없이 연결이 닫힘(클라이언트에서 `RemoteDisconnected`)이고 서버 로그에 예외가 남음. 두 번째 요청은 200. `server.workers[0].is_alive()`가 참 | 미실행 | `TP-06`, `TP-07`. 엔진 예외는 `_execute`가 500으로 바꿔서 워커까지 오지 않으니, 핸들러 밖으로 나가는 예외를 일부러 만들어요. 로그는 `handle_error()`가 `logger.exception()`으로 남겨요 |
| T-TP-05 | 스레드 | 요청을 읽을 때 정해진 시간 동안 데이터가 오지 않으면 연결을 닫는다 | `QueryHandler.timeout`을 0.5초로 바꾸고 서버 실행 | 바디를 보내지 않는 연결을 열고 응답을 기다림 | 약 0.5초 뒤 응답 없이 연결이 닫힘(`recv()`가 `b""`). 그 뒤 보낸 요청은 200 | 미실행 | `TP-08`. 503이 아니에요. 실제 값은 5초지만 테스트 시간을 줄이려고 0.5초로 바꿔요 |
| T-LK-01 | 동시성 | INSERT를 동시에 여러 번 보내도 id가 겹치지 않는다 | 빈 `users`, 서버 실행(`workers=4`) | 스레드 8개에서 INSERT를 25번씩 동시에 보냄(총 200번) | 응답 200개 모두 201. `inserted_id`가 1~200에 중복·누락 없음. `SELECT * FROM users`의 `row_count: 200`. id 1~200 각각 `WHERE id = n`으로 조회됨 | 미실행 | `LK-02`, `LK-03`. 두 번만 보내면 경합이 거의 안 생겨서 많이 보내요. 동시 요청 8개는 워커와 큐 크기의 합(20)보다 작아서 503이 나지 않아요 |
| T-LK-02 | 동시성 | INSERT 도중 SELECT해도 반쯤 써진 행을 읽지 않는다 | `users`에 id 1~3 저장, 서버 실행. 서버 엔진의 `storage.append`를 감싸 한 줄을 두 번에 나눠 쓰고 그 사이 0.005초 쉬게 함 | 한 스레드는 INSERT 100번, 다른 스레드는 그동안 `SELECT * FROM users`를 반복 | 모든 SELECT가 200. 모든 행이 값 3개(`[int, str, int]`). `row_count`는 이전 응답보다 줄지 않음 | 미실행 | `LK-02`. 한 줄은 `write()` 한 번에 써져서 그대로는 경합이 거의 안 생겨요. 쓰기를 나눠 끼어들 틈을 일부러 만들어요. 락이 없으면 값이 빠진 행이 200으로 섞여 나와요 |
| T-LK-03 | 동시성 | 한 명령어를 실행하는 동안 다른 명령어가 끼어들지 못한다 | 빈 `users`로 `Executor` 생성. `storage.append`를 감싸 쓰기 뒤에 0.05초 쉬게 함 | 스레드 2개에서 `run(INSERT)`를 동시에 호출 | 두 결과의 `inserted_id`가 1과 2로 다름. `users.csv` 2줄, 트리에서 1과 2 모두 조회됨 | 미실행 | `LK-03`. 쉬는 시간으로 id 발급과 `next_id` 증가 사이에 끼어들 틈을 만들어요. 락이 없으면 둘 다 id 1을 받아요 |
| T-LK-04 | 동시성 | 한 테이블에서 워커가 실행하는 동안 다른 워커는 그 테이블에서 실행하지 못한다 | `Executor` 생성. `run_insert`, `run_select`를 감싸 들어갈 때 카운터 +1, 0.05초 쉼, 나갈 때 −1, 최댓값 기록 | 스레드 4개에서 INSERT와 SELECT를 섞어 동시에 호출 | 카운터 최댓값이 1 | 미실행 | `LK-02`. INSERT와 SELECT가 같은 락을 쓰는지도 같이 확인돼요. 락이 없으면 최댓값이 4예요 |
| T-LK-05 | 동시성 | 실행 중 예외가 나도 락이 풀린다 | `Executor` 생성. `storage.append`가 처음 한 번만 `OSError`를 던지게 함 | INSERT를 두 번 호출 | 첫 번째는 `OSError`. 두 번째는 1초 안에 성공(멈추지 않음) | 미실행 | `LK-04`. 락을 잡고 놓지 않는 버그를 잡는 테스트예요. 두 번째 호출은 별도 스레드에서 실행하고 `join(timeout=1)`로 기다려요 |
